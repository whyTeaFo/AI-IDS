# 基于机器学习的网络入侵检测与实时告警系统设计与实现

**课程设计报告**

---

## 摘要

网络入侵检测系统（Intrusion Detection System, IDS）是网络安全防护体系中的关键环节。传统的基于签名的检测方法只能识别已知攻击模式，面对不断演变的攻击手法时存在天然的滞后性。本文设计并实现了一套基于机器学习的网络入侵检测与实时告警系统（AI-IDS），完成了从原始网络流量到可视化告警看板的完整链路。

系统以 CICIDS2017 公开数据集为基础，构建了「数据包 → 流 → 流特征 → AI 模型」的处理管线。在数据层面，本文针对该数据集已知的脏数据问题（编码损坏的标签、无穷值、25 万条重复记录、8 个常量列）设计并实施了完整的清洗流程，将 3,119,345 条原始记录清洗为 2,573,698 条有效样本。在模型层面，本文对比了随机森林、XGBoost 与多层感知机三种算法在二分类与多分类两个任务上的表现，并围绕类别不平衡处理、未知攻击泛化能力、特征可解释性与评估方法有效性四个研究点展开了实验分析。在系统层面，本文实现了基于 FastAPI 的推理服务、基于 SQLite 的告警存储与基于 ECharts 的实时监控看板，并开发了从 pcap 文件与网卡实时提取流特征的流量解析模块。

本研究的核心发现有以下四点。**其一**，CICIDS2017 存在严重的采样偏差——除 Bot（8 个源 IP）与 DDoS（2 个）外每一类攻击都只来自一台攻击机，这使「按源 IP 分组划分」这一常规防泄露方法在该数据集上完全无法使用。**其二**，随机划分下 99.92% 的准确率与 0.9972 的 MCC 严重高估了模型的泛化能力：按时间划分后多分类宏 F1 从 0.9550 跌至 0.1151。**其三**，类别不平衡的有效对策是**调整损失权重而非合成样本**——类别加权把平衡准确率从 0.9328 提升到 0.9771，而 SMOTE 在少数类训练样本仅 26 条时对最困难的类毫无改善。**其四**，模型对未知攻击的检出能力远弱于已知攻击（0.0000~0.6854 vs 0.9112~0.9739），其中最隐蔽的 Bot 攻击在两个任务上均为零检出，说明它学到的主要是攻击指纹而非「正常流量的样子」。

**关键词**：入侵检测；机器学习；CICIDS2017；XGBoost；类别不平衡；可解释性

## 1 绪论

### 1.1 研究背景

随着网络攻击手段的不断演化，单纯依赖特征库匹配的传统检测方法面临越来越大的挑战。签名检测的核心假设是「已知攻击的特征是固定的」，但现实中的攻击者可以通过变形、加壳、分片等手段轻易绕过静态规则。更严重的是，从漏洞披露到攻击工具出现的时间窗口正在不断缩短，签名库的更新速度难以跟上攻击的演变速度。

机器学习方法为解决这一问题提供了新思路。其核心思想是不去描述「攻击长什么样」，而是从大量标注数据中自动学习「什么样的通信行为是异常的」。理论上，这种方法能够识别出训练时未曾出现过的攻击变种——这正是本文重点研究的未知攻击泛化能力。

### 1.2 研究目标

本文的目标不是追求某个模型在某个数据集上的最高准确率，而是完成一个具备实际可用性的完整系统，并回答以下四个问题：

1. **不同机器学习模型在网络入侵检测任务上的性能差异如何？** 树模型与神经网络在结构化流量特征上的表现孰优孰劣？
2. **类别不平衡对检测效果的影响有多大？** 加权损失与过采样两种处理策略各自的收益与代价是什么？
3. **模型能否识别训练时未见过的攻击类型？** 这是 IDS 面对真实网络的核心能力。
4. **常用的随机划分评估方法是否可靠？** 以 CICIDS2017 为例，其给出的高准确率有多少是真实的？

### 1.3 本文工作

- 完成了 CICIDS2017 数据集的完整清洗流程，识别并修复了包括编码损坏标签、无穷值、大规模重复记录在内的多个数据质量问题；
- 实现了随机森林、XGBoost、多层感知机三种模型的训练与评估管线，在二分类与多分类任务上进行了系统对比；
- 针对四个研究点设计了对照实验，并对实验结果进行了分析；
- 实现了完整可运行的系统，包括 FastAPI 推理服务、SQLite 告警存储、ECharts 可视化看板，以及基于 tshark 的 pcap/网卡流量特征提取模块；
- 发现并记录了 CICIDS2017 数据集的一个重要采样偏差，该偏差使得文献中常见的两种防泄露划分策略之一在该数据集上无法使用。

## 2 相关技术背景

### 2.1 从数据包到流特征

网络入侵检测的输入可以是原始数据包，也可以是流（Flow）的统计特征。直接以原始数据包作为模型输入（如使用 CNN 处理字节序列）计算开销大且对变长序列不友好；而以流为单位提取统计特征后，每条流成为一个固定维度的向量，更适合经典机器学习方法。

本文采用后者。一条流定义为具有相同五元组（源 IP、源端口、目标 IP、目标端口、协议）的连续通信。以一次 HTTP 请求为例：

```
192.168.1.20:52131 ──TCP──▶ 192.168.1.100:80
    duration = 1.2s
    fwd_packets = 18,  bwd_packets = 22
    fwd_bytes = 12800, bwd_bytes = 45210
    ...
```

这些统计量构成的向量即模型的输入。这种做法的优点是特征具备明确的物理含义，便于解释与调试；缺点是丢失了载荷内容信息，无法识别依赖具体内容的攻击。

### 2.2 数据集简介

CICIDS2017 由加拿大网络安全研究所（Canadian Institute for Cybersecurity）于 2017 年发布，是入侵检测领域使用最广泛的公开数据集之一。数据集在真实的测试网络中采集，包含正常流量与多种攻击流量，攻击类型覆盖拒绝服务、端口扫描、暴力破解、Web 攻击、僵尸网络与内网渗透等主要类别。

该数据集的一个重要特点是**每个采集日只包含特定类型的攻击**，具体分布见表 3-1。这一特点直接决定了后文数据划分策略的选择。

### 2.3 评价指标

在类别极不平衡的入侵检测任务中，准确率（Accuracy）是误导性最强的指标。假设攻击流量占比 1%，一个将所有样本都判为正常的模型即可获得 99% 的准确率，但其检测能力为零。

因此本文以以下指标为主：

- **召回率（Recall）**：真实攻击中被检出的比例。在安全场景中，漏报的代价通常远高于误报。
- **F1 分数**：精确率与召回率的调和平均。
- **MCC（马修斯相关系数）**：综合考虑混淆矩阵四个象限，取值范围 [-1, 1]。在不平衡数据上比 F1 更能反映真实性能——模型全猜多数类时，F1 可能不低，但 MCC 会趋近于 0。
- **假阳性率（FPR）**：正常流量被误判为攻击的比例。这是决定系统能否落地的关键指标——运维人员被误报淹没后会直接关闭告警系统。
- **宏平均 F1（macro-F1）**：各类别 F1 的算术平均，不受类别样本量影响，能暴露「多数类很好、少数类全错」的情况。

## 3 数据集与数据预处理

### 3.1 数据集版本的选择

CICIDS2017 官方发布过两个不同版本的 CSV 数据，这是使用该数据集时最容易踩的坑之一：

| 版本 | 特征列数 | 是否含身份列 | 体积 |
|---|---|---|---|
| `MachineLearningCSV` | 78 | **否** | 235 MB |
| `GeneratedLabelledFlows` | 84 | **是** | 284 MB |

网络上的大量教程指向的是 `MachineLearningCSV` 版本，但该版本**删除了 Flow ID、Source IP、Source Port、Destination IP、Timestamp 五列身份信息**。

这个差异对本文的研究有决定性影响：缺少 Source IP 意味着无法进行「按主机分组划分」的实验，也无法在告警中将预测结果关联回具体的攻击源主机——而对于一个告警系统而言，「谁在攻击」恰恰是最需要的信息。

因此本文最终选用 `GeneratedLabelledFlows` 版本。

### 3.2 数据加载中的编码问题

在加载阶段，本文发现 CICIDS2017 存在一个隐蔽的编码损坏问题，Web 攻击类别的标签在不同版本中损坏形式不同：`GeneratedLabelledFlows` 版本中，`Web Attack` 与 `Brute Force` 之间的字节是 `0x96`（在 cp1252 中对应短破折号），不是合法 UTF-8 序列；`MachineLearningCSV` 版本中，同样位置的字节是 `EF BF BD`，即替换字符 U+FFFD 的 UTF-8 编码。第二种情况说明**该损坏在官方生成数据时就已经产生**——UNB 团队用错误的编码读取了原始标签并写入了文件，因此换用任何编码都无法恢复，只能作为噪声处理。

由于同一批文件中合法与非法字节并存，本文采用在读取时使用 `errors='replace'`、使所有非法字节统一退化为 U+FFFD，再在标签清洗阶段按字符剥离的方案。这把「多种损坏」收敛为「一种损坏」，下游只需处理一个字符。清洗函数按 Unicode 类别处理：控制字符（Cc）、格式字符（Cf）、各类破折号（Pd）与特殊空格（Zs）统一替换为普通空格，随后折叠连续空白。三种损坏形式的处理结果一致：

```
'Web Attack\x96 Brute Force'   →  'Web Attack Brute Force'
'Web Attack\xad Brute Force'   →  'Web Attack Brute Force'
'Web Attack� Brute Force' →  'Web Attack Brute Force'
```

此外，`Thursday-WorkingHours-Morning-WebAttacks` 文件中存在 288,602 条**空标签**记录。这类记录被 pandas 读取为 NaN，若直接用 `str()` 转换会得到字面量字符串 `'nan'`，看起来像一个合法但未识别的类别，从而绕过了缺失值判断逻辑。本文在标签清洗函数中显式识别 NaN 并返回空字符串，交由后续步骤按缺失值处理。

### 3.3 标签归并

原始数据集包含 15 种标签，且部分标签存在拼写不一致。本文按攻击原理将其归并为 8 个类别：

| 归并后类别 | 原始标签 |
|---|---|
| `BENIGN` | BENIGN |
| `DoS` | DoS Hulk、DoS GoldenEye、DoS slowloris、DoS Slowhttptest、Heartbleed |
| `DDoS` | DDoS |
| `PortScan` | PortScan |
| `BruteForce` | FTP-Patator、SSH-Patator |
| `WebAttack` | Web Attack Brute Force、Web Attack XSS、Web Attack Sql Injection |
| `Bot` | Bot |
| `Infiltration` | Infiltration |

归并的依据是攻击的作用机理：四种 DoS 变体虽然实现方式不同（缓冲区填充、慢速连接等），但对系统的危害与响应方式一致；Heartbleed 本质上是利用 OpenSSL 漏洞读取内存，造成资源耗尽，归入 DoS 大类。

### 3.4 数据清洗

清洗流程按以下顺序执行，顺序的设计有明确理由：

**步骤 1：标签映射。** 必须先做，否则后续删除缺失值时会连带丢弃标签异常的样本，且无法统计各类别的真实数量。

**步骤 2：无穷值截断。** `Flow Bytes/s` 与 `Flow Packets/s` 两列存在无穷值，源于 CICFlowMeter 在流持续时间极小时做除法。**这些列不能用 `dropna` 直接删除**——无穷值只出现在 duration≈0 的流中，而这类流包含大量 PortScan 与 DDoS 样本，直接删除会成片丢失攻击样本。本文用该列 0.999 分位数作上界截断；选择分位数而非最大值，是因为最大值本身可能就是无穷值派生结果，用它作上界等于没有截断。

**步骤 3：缺失值删除。** 按特征列判断缺失并删除对应行。

**步骤 4：重复行删除。** 这是影响最大的一步：数据集包含大量特征与标签完全一致的重复记录（尤其 DoS 与 DDoS），若不删除，训练集与测试集之间会存在大量完全相同样本，直接导致评估虚高。本步骤删除 255,480 条记录。

**步骤 5：常量列删除。** `CWE Flag Count`、`Fwd Avg Bytes/Bulk` 等 8 列在所有样本上恒为 0，对模型没有贡献，只会稀释特征重要性。

### 3.6 特征选择

本文从 70 个可用特征中剔除了以下身份相关列，理由是它们会造成数据泄露：

| 剔除的列 | 理由 |
|---|---|
| `Flow ID` | 每条流唯一，纯索引，无泛化价值 |
| `Source IP` | 会让模型记忆主机身份而非学习行为 |
| `Destination IP` | 同上 |
| `Timestamp` | 会让模型学到「某时间段 = 攻击」 |
| `Source Port` | 客户端临时端口，高基数噪声 |
| `_source_file` | 数据来源文件名，与标签高度相关 |

其中 `_source_file` 是本文在开发过程中通过冒烟测试发现的一个真实泄露源。该列记录每条流来自哪个采集日，而 CICIDS2017 的每个采集日只包含特定攻击（周三只有 DoS，周五下午只有 PortScan 与 DDoS）。若该列进入特征，模型只需记住「这条来自周三的文件」就能答对，准确率会虚高到 99% 以上，但完全没有检测能力。

`Destination Port` 予以保留。服务端口具有真实语义（22 表示 SSH、80 表示 HTTP），是 PortScan 类攻击的重要判别依据，文献中普遍保留。

### 4.2 模块划分

| 模块 | 职责 | 关键设计 |
|---|---|---|
| `aiids.data` | 数据加载、清洗、划分 | 集中管理数据集的脏数据修补规则 |
| `aiids.features` | 特征管道 | 列顺序绑定与持久化，防止推理时特征错位 |
| `aiids.models` | 模型训练与评估 | 支持三种划分策略与多种评估口径 |
| `aiids.imbalance` | 类别不平衡处理 | class_weight 与 SMOTE 两种策略 |
| `aiids.explain` | 可解释性分析 | 内置重要性与 SHAP 归因 |
| `aiids.generalize` | 未知攻击泛化实验 | 留一类攻击法 |
| `aiids.flow` | 流量特征提取 | tshark 解析与双向流聚合 |
| `aiids.alert` | 告警引擎 | 置信度阈值、去重窗口、严重级别 |
| `aiids.db` | 数据持久化 | SQLite，WAL 模式支持并发读写 |
| `aiids.api` | HTTP 服务 | FastAPI，托管静态前端 |

### 4.3 特征管道的设计

特征管道（`FeaturePipeline`）是系统中一个容易被忽视但极其关键的组件。它并非简单的 `StandardScaler` 封装，而是解决了三个工程问题：

**其一，列顺序的一致性。** scikit-learn 的标准化器只识别数组中的位置，不识别列名。若推理时传入的 DataFrame 列顺序与训练时不同，模型会给出完全错误的预测——没有异常、没有警告，只是结果全错。本文将列名绑定进管道，顺序不一致时直接报错。

**其二，管道与模型的配套持久化。** 模型与管道必须成对使用。若推理时重新拟合一次标准化器，得到的均值方差会与训练时不同，导致线上与离线结果不一致。

**其三，避免重复变换。** 特征管道会原地替换数据集中的特征表。在同时训练多个模型时，若每个模型各自调用一次变换，数据会被标准化两次。本文为此在划分结果对象上增加了状态标记，重复变换时直接报错。

## 5 模型与实验设计

### 5.1 模型选择

本文选择三种模型，它们各自承担不同的角色：

**随机森林（Random Forest）—— 基线模型。** 无需精细调参即可获得较好性能，作为「树模型能做到什么程度」的参照。其袋外误差与特征重要性都便于分析。

**XGBoost —— 主模型。** 在结构化表格数据上通常表现最佳，训练速度快，支持早停，且提供原生特征重要性。本文预期它是三者中表现最好的。

**多层感知机（MLP）—— 深度学习对照组。** 用于回答「在这个任务上神经网络是否值得」的问题。考虑到流量特征本质上是结构化的表格数据，缺乏图像或序列数据中的空间/时序局部性，本文预期神经网络难以超越梯度提升树。这个「打不过」的结论本身也具备研究价值。

### 5.2 数据划分策略

本文实现了三种划分策略，它们对应不同的评估目的：

**随机分层划分（random）。** 这是文献中最常见的做法，按类别比例随机划分训练集、验证集与测试集。本文将其作为对照基线。

**按时间划分（time）。** 按采集日期切分：周一至周三作为训练期，周四至周五作为测试期。由于 CICIDS2017 每天的流量内容差异极大，这一划分使得**测试期的 6 个攻击类别在训练期完全没有出现过**，构成真正的零日攻击场景。

**按源 IP 分组划分（group）。** 设计意图是确保同一主机产生的所有流只出现在训练集或测试集的一侧，从而消除「模型靠记忆主机特征蒙对」的泄露路径。

### 5.3 关于按主机划分的发现

按主机分组划分是评估模型泛化能力的常规做法，本文在实施时发现**该方法在 CICIDS2017 上会严重退化**，且退化的方式因任务而异，值得分三点说明。

统计各攻击类别的源 IP 数量，结果如表 5-1 所示。

**表 5-1 各攻击类别的源 IP 分布**

| 类别 | 流数 | 不同源 IP 数 | 最大单 IP 占比 | 前 3 个 IP 占比 |
|---|---:|---:|---:|---:|
| BENIGN | 2,147,838 | 17,005 | 13.9% | 29.7% |
| Bot | 1,953 | 8 | 36.1% | 68.4% |
| BruteForce | 9,152 | **1** | 100.0% | 100.0% |
| DDoS | 128,016 | **2** | 100.0% | 100.0% |
| DoS | 193,741 | **1** | 100.0% | 100.0% |
| Infiltration | 36 | **1** | 100.0% | 100.0% |
| PortScan | 90,819 | **1** | 100.0% | 100.0% |
| WebAttack | 2,143 | **1** | 100.0% | 100.0% |

除 Bot（8 个源 IP）与 DDoS（2 个）外，**其余每一类攻击都只来自一台攻击机**，这意味着按源 IP 分组划分时一个攻击类别会被整体推到划分的某一侧，该类别在另一侧完全消失。这一采样偏差对实验的影响按任务不同分为三种情况。

**第一，在多分类任务上该划分确实无法使用。** 测试集丢失了 8 个类别中的 6 个，模型的逐类评估退化为「对 2 个类别打分」。本文对此加入了退化检测：当测试集丢失超过半数的类别时直接报错并说明原因，而不是产出一个「准确率 99% 但只评估了正常流量」的虚假结果。

**第二，在二分类任务上该划分可以运行，但评估样本量被严重压缩。** 因为二分类目标变量只有 BENIGN/ATTACK，攻击类别被整体推到训练侧并不会让测试集丢失类别。代价是测试集中的攻击样本从随机划分下的 **85,172 条骤降至 936 条**，以 936 条样本估计的召回率，其 95% 置信区间宽度约为 ±2.4 个百分点，指标可信度已明显低于随机划分。这一步必须说明：若只看输出，实验「正常完成」了，问题只体现在一个容易被忽略的样本数上。

**第三，也是最值得关注的一点：该划分暴露了模型严重的主机泛化缺陷。** 在该划分下模型对**来自未见主机的攻击**的检出率仅为 **17.5%（随机森林）/ 18.8%（XGBoost）/ 15.5%（MLP）**，而同一数据集在随机划分下的攻击召回率为 **99.7%**——一旦攻击来自训练时没见过的源主机，检出能力下降到不足原来的五分之一。与此同时三个模型的准确率仍有 **0.9976 / 0.9981 / 0.9973**，因为测试集中 BENIGN 占 99.8%，全部判为正常即可拿到 99.8% 的准确率。

这是全文「准确率陷阱」最有力的例证：**同一组模型，准确率看上去几乎无懈可击，实际检出能力却只有 18%**。表 5-2 给出三种划分下的对照——按主机划分的准确率（99.81%）甚至高于按时间划分（86.35%），检出率却是三者中最低的。**准确率在高度不平衡的数据上不携带任何关于检出能力的信息**，这正是本文在全部实验中同时报告平衡准确率、宏 F1 与 MCC 的原因。

**表 5-2 三种划分下的攻击检出能力对照（XGBoost）**

| 划分方式 | 准确率 | 测试集攻击样本数 | 攻击召回率 | 假阳性率 |
|---|---:|---:|---:|---:|
| 随机分层 | 0.9992 | 85,172 | 0.9984 | 0.00065 |
| 按时间 | 0.8635 | 222,967 | 0.3648 | 0.00016 |
| 按源 IP 分组 | 0.9981 | **936** | **0.1880** | 0.00041 |

需要指出的是，这一结果反映的是**数据集本身的采样偏差**，而非代码缺陷：CICIDS2017 在封闭测试床中采集，攻击流量在源 IP 上高度集中，模型确实学到了这些主机特有的流量特征。

基于以上分析，本文采用**按时间划分**作为严格划分方案。它同样达到了消除泄露的目的（测试期 6 个攻击类别在训练期完全未见），且保留了 8.5 万条攻击样本，评估结果具备统计意义。

### 5.4 四个研究点的实验设计

**研究点①：类别不平衡处理。** 在相同数据、相同划分、相同模型的前提下对比三种策略：原始数据（基线）、`class_weight='balanced'`（按类别频率倒数加权，零内存开销但不增加信息量）、SMOTE 过采样（插值合成新样本，增加信息量但计算代价高）。

需要说明 SMOTE 在本数据集上的工程约束：训练集中 BENIGN 类约 170 万条，若用 `sampling_strategy='not_majority'`，其余 7 类都会被补齐到同一规模，总量达 1200 万行、内存约 3.6 GB，加上 kNN 近邻搜索开销会导致内存耗尽。因此本文采用 **capped 策略**，为少数类设定目标样本数上限（默认 5 万条）——这一取舍在真实系统中同样成立。

**研究点②：未知攻击泛化。** 采用留一类攻击法（leave-one-attack-out）：将某一类攻击从训练集与验证集中完全移除，在测试集上考察检出能力。二分类上它测量真正的异常发现能力（模型学的是「正常流量长什么样」，未知攻击虽没学过，但「不像正常流量」理论上应能被标记）；多分类上被留出类的 F1 必然为 0，此时有意义的观察是**误判去向**。

**研究点③：可解释性。** 树模型的内置特征重要性提供全局视角，SHAP 值提供逐样本的方向性归因，可回答「这条被误报的流是哪个特征导致的」。

**研究点④：划分方式对评估结果的影响。** 对比随机划分与按时间划分下的模型表现，两者指标之差即为随机划分高估的部分。

### 5.5 模型超参数的确定

初版配置（随机森林 200 棵不限深度的树、MLP 批大小 512 且最大迭代 100 轮）在 185 万训练样本上跑一轮完整实验矩阵需要 3 小时以上，其中 MLP 单个任务即需 30 分钟以上。分析后进行了如下调整：

**随机森林：200 棵 → 100 棵，并设置 `min_samples_leaf=2`。** 随机森林的方差随树数量按 1/√n 下降，从 100 棵增加到 200 棵的收益不足 1%，训练时间却翻倍。`min_samples_leaf=2` 是更关键的改动：在 250 万样本的规模下，叶节点只含 1 个样本的树必然过拟合，且树会生长到极深；将其限制为 2 可大幅压缩树规模，而精度损失可忽略。

**MLP：批大小 512 → 2048，最大迭代 100 → 40。** 185 万样本按批大小 512 划分为约 3600 个批次，100 轮即 36 万次参数更新，其中绝大部分梯度方向是冗余的。增大批大小后每轮仅需约 900 次更新。配合早停机制，实际训练通常在 15 至 25 轮内收敛。

调整后单轮实验矩阵耗时降至约 40 分钟。所有实验均使用固定随机种子 42 以保证可复现性。

### 6.2 研究点①：类别不平衡处理

实验在相同数据、相同划分（多分类·随机）、相同模型（XGBoost）下对比三种策略。测试集中 BENIGN 占 83.5%，四个少数类的样本数分别为 Bot 391、WebAttack 429、Infiltration 7、BruteForce 1830——**样本极不平衡是这一研究点要解决的问题**。

**表 6-4 三种不平衡处理策略的总体指标（XGBoost，多分类，随机划分）**

| 策略 | 准确率 | 平衡准确率 | 宏精确率 | 宏 F1 | MCC | 训练耗时 |
|---|---:|---:|---:|---:|---:|---:|
| 原始数据（不处理） | 0.9992 | 0.9328 | 0.9845 | **0.9550** | **0.9972** | 199.9 s |
| **类别加权** | 0.9991 | **0.9771** | 0.9381 | 0.9548 | 0.9968 | 462.9 s |
| SMOTE 过采样 | 0.9990 | 0.9607 | 0.9339 | 0.9431 | 0.9967 | 299.3 s |

|---|---:|---:|---:|---:|
| Bot | 391 | 0.7647 | 0.9616 | **0.9770** |
| WebAttack | 429 | 0.9860 | **1.0000** | 0.9977 |

| 类别 | 训练集样本数 | 权重 | 相对 BENIGN 的倍数 |
|---|---:|---:|---:|
| Infiltration | 26 | 8908.95 | 59478.6 |
| Bot | 1406 | 164.75 | 1099.9 |
| WebAttack | 1542 | 150.22 | 1002.9 |
| BruteForce | 6590 | 35.15 | 234.7 |

| DoS | 139494 | 1.66 | 11.1 |
| BENIGN | 1546443 | 0.15 | 1.0 |

**类别加权是三者中最优的策略，且优势体现在最该被修复的那一类上。** 平衡准确率从 0.9328 提升到 **0.9771**（+0.0443），Bot 召回率从 0.7647 提升到 0.9616——即原本每 4 条 Bot 流量漏掉 1 条，现在 25 条才漏 1 条。而宏 F1 几乎不变（0.9550 → 0.9548）。

它有效的机制很清楚：**类别加权不改变数据分布，只改变优化目标**——表 6-6 显示，加权后 Infiltration 的每条样本在损失中的分量是 BENIGN 的 5.9 万倍，模型因此愿意为少数类的分类错误付出更大代价。**代价是训练时间翻倍以上（199.9 s → 462.9 s）**：降权后的 BENIGN 样本需要更多轮次才能收敛，实测跑满 400 轮才早停，而未加权时 200 轮左右即收敛。这一代价在离线训练下可以接受，但若需频繁重训练则应纳入考量。

**SMOTE 反而不如类别加权，这一结果与直觉相反，但原因可以被精确解释。** 表 6-5 中 SMOTE 的平衡准确率只有 0.9607、宏 F1 0.9431 为三者最低；更关键的是 **Infiltration 的召回率停在 0.7143，与完全不处理时一模一样**。原因在于**少数类的绝对样本量，而不是不平衡比**：训练集中 Infiltration 只有 **26 条真实样本**，而 capped 策略要求合成到 5 万条，等于用 26 个点插值出 4.9 万个近邻副本——这些样本密集堆积在原 26 个点的邻域内，**不携带任何新信息**，反而稀释了决策边界。Bot（1406 条 → 5 万）与 WebAttack（1542 条 → 5 万）情况类似：召回率上去了，精确率却明显下滑（Bot 精确率 0.8979 → 0.6702），模型变得"爱报攻击"。由此得到一个有普遍意义的结论：**26 条真实样本的价值高于 4.9 万条由它们插值生成的样本**，因此在小样本少数类上，调整损失权重比合成样本更有效。

**宏 F1 在本实验中不具备区分度，这是一处必须点明的指标陷阱。** 三种策略的宏 F1 差异不到 0.012（0.9431~0.9550），而平衡准确率的差异达 0.044——后者是前者的 3.7 倍。原因是宏 F1 同时受精确率与召回率影响：类别加权把 Bot 召回率从 0.7647 提到 0.9616，却把精确率从 0.8979 压到 0.6899，一升一降相互抵消。而**平衡准确率（等价于宏召回率）直接反映"少数类有没有被放弃"**，正是本问题要回答的内容。**因此本节结论一律引用平衡准确率。** 若只看宏 F1，会得出"三种策略没有差别、不必处理"的错误结论。

**结论：** 类别不平衡处理应优先选择**类别加权**——它在几乎不损失多数类性能的前提下大幅提升了少数类召回率，且实现成本最低。SMOTE 只在少数类有足够绝对样本量时才有价值；当少数类训练样本不足百条时，过采样只是在放大噪声。评估这类方法必须使用平衡准确率而非宏 F1，否则会彻底掩盖效果。

### 6.3 研究点②：未知攻击泛化能力

本实验采用**留一类攻击法**（leave-one-attack-out）：把某一类攻击从训练集与验证集中**完全移除**，再在包含该类样本的测试集上考察模型的检出能力。这是四个研究点中最贴近真实部署场景的一个——攻击手法必然演变，IDS 一定会遇到训练时没见过的攻击。其严格程度也高于第 6.5 节的按时间划分：后者让**多个**攻击类在训练期缺席，而留一类实验是**精确隔离单一类别**，可逐类观察模型对特定攻击类型的盲区。

**表 6-7 未知攻击检出率（XGBoost，随机划分）**

| 留出类 | 任务 | 留出样本数 | 未知攻击检出率 | 已知攻击检出率 | 检出率差距 |
|---|---|---:|---:|---:|---:|
| Bot | 二分类 | 395 | **0.0000** | 0.9739 | 0.9739 |
| WebAttack | 二分类 | 426 | 0.6854 | 0.9341 | 0.2486 |
| Infiltration | 二分类 | 7 | **0.0000** | 0.9559 | 0.9559 |
| Bot | 多分类 | 391 | **0.0000** | 0.9506 | 0.9506 |
| WebAttack | 多分类 | 429 | 0.3939 | 0.9112 | 0.5173 |
| Infiltration | 多分类 | 7 | **0.0000** | 0.9602 | 0.9602 |

> 「已知攻击检出率」是同一测试集上**其余**攻击类的平均检出率，作为对照。
> 两者差距越大，说明模型越依赖记忆已知攻击的指纹，而不是真正理解
> 「什么样的流量不像正常通信」。

**表 6-8 被留出类在多分类下的误判去向**

| 留出类 | 判为 BENIGN | 判为 DoS | 判为 PortScan |
|---|---:|---:|---:|
| Bot | 100.00% | — | — |
| WebAttack | 60.61% | 35.20% | 4.20% |
| Infiltration | 100.00% | — | — |

**模型对训练时从未出现过的攻击类，检出能力大幅下降。** 表 6-7 中，已知攻击的检出率稳定在 **0.91~0.97**，而未知攻击的检出率落在 **0.0000~0.6854** 之间，六组实验的平均差距达 **0.768**。这说明模型学到的决策边界是围绕**已知攻击样本**构建的，而不是围绕**正常流量的分布**构建的——如果它真的理解了后者，那么「不像正常流量」这一判据应当对任何攻击都成立。

**Bot 在两个任务上的检出率都是 0.0000，这是本实验最极端的发现。** 395 条（二分类）/ 391 条（多分类）Bot 流量**全部**被判为 BENIGN，而无一条被标记为异常，已知攻击的对照检出率则为 0.9739 / 0.9506——去掉 Bot 之后模型的整体召回率几乎没有下降，它对这类攻击是**完全盲**的。这可由攻击机理得到解释：Bot 感染主机后与 C2 之间是**低速、周期性、长时间静默**的回连通信，流量体量小、包间隔长；而模型从 DoS、DDoS、PortScan 等训练类中学到的「异常」模式是**高频发包、间隔极小、包长规整**（与第 6.4 节「空闲时间均值」高居重要性第二位的发现一致）。Bot 的通信节律恰好落在正常流量的区间内，因而完全没有触发模型学到的异常判据。这也与第 6.2 节互相印证：Bot 正是四个少数类里召回率最低的一个（未处理时仅 0.7647）。

**WebAttack 是唯一被部分检出的未知攻击，但其多分类下的失败方式很有信息量。** 二分类下 68.54% 被检出，说明它在流量统计特征上确实与正常流量有差异；多分类下检出率降到 39.39%，且**被误判为 DoS 的比例高达 35.20%**——多分类不仅要判断「异常」，还要在 8 个类别里选一个最接近的，而 WebAttack 在训练时不存在，模型只能将其归入行为最相似的已知攻击类。这个误判去向直接指出了改进方向：**当前的流统计特征无法区分「应用层的 HTTP 异常请求」与「传输层的高频洪泛」**——二者都可能表现为短时间内的连续请求，但一个是低速发送畸形请求，另一个是靠请求量压垮服务。要区分它们必须引入载荷层面的特征（URI 模式、参数结构、请求方法分布），这已超出流统计量的表达能力，也是第 8.3 节把「引入载荷特征」列为未来工作首项的直接依据。

**Infiltration 的 0.0000 不能作为独立结论使用。** 该类在测试集中仅有 **7 条样本**，如此样本量下检出率的置信区间极宽，0/7 与 7/7 都无法把真实检出率约束在任何有意义的区间内。本文如实报告该数值，但**不基于它得出任何结论**——Infiltration 全数据集仅 36 条样本，任何涉及该类的量化结论都应谨慎对待。

**二分类的检出率系统性地高于多分类，但 Bot 是例外。** 对 WebAttack，二分类 0.6854 明显优于多分类 0.3939——二分类只需回答「是否异常」这一较粗的问题。但 Bot 在两个任务上都是 0.0000，说明它的失败与「无法归类」无关，而是**根本没有被识别为异常**：前者是分类粒度问题，后者是检测能力的缺失。

**结论：** 模型并不具备真正的未知攻击发现能力，其表现高度依赖训练集中是否出现过同类攻击，**因此不能作为独立防线部署**，必须与签名检测、流量基线告警等互补手段配合。若要提升未知攻击检出能力，方向是引入载荷特征（针对 WebAttack 这类应用层攻击）与基于正常流量分布的单类建模（针对 Bot 这类低速隐蔽通信），而不是继续在已知攻击类上增加样本。

### 6.4 研究点③：特征可解释性

采用两种互补方法：XGBoost 的增益型特征重要性提供全局视角，SHAP 值提供逐样本的方向性归因。

**表 6-9 XGBoost 多分类（随机划分）特征重要性 Top 10**

| 排名 | 特征 | 重要性占比 | 累计 |
|---:|---|---:|---:|
| 1 | Bwd Packet Length Std（后向包长标准差） | 16.46% | 16.46% |
| 2 | Idle Mean（空闲时间均值） | 10.79% | 27.25% |
| 3 | Bwd Packet Length Mean（后向包长均值） | 7.32% | 34.57% |
| 4 | Max Packet Length（最大包长） | 6.68% | 41.25% |
| 5 | act_data_pkt_fwd（前向实际数据包数） | 5.60% | 46.85% |
| 6 | Total Length of Fwd Packets（前向字节数） | 5.28% | 52.13% |
| 7 | Average Packet Size（平均包大小） | 4.11% | 56.24% |
| 8 | Fwd Packet Length Max（前向包长最大值） | 3.72% | 59.96% |
| 9 | Packet Length Std（包长标准差） | 3.25% | 63.22% |
| 10 | Packet Length Variance（包长方差） | 3.20% | 66.42% |

前 10 个特征累计贡献 **66.4%**，重要性分布高度集中。两个特征值得单独说明：

**后向包长标准差（16.46%）位列第一。** 「后向」指服务器到客户端方向的包，该特征衡量响应包大小的离散程度。正常 HTTP 会话的响应包大小分布多样（不同大小的页面资源），而自动化攻击工具产生的响应往往高度规整（扫描器的固定长度响应、DDoS 反射的等长包），因此响应包长方差成为强判别信号。这说明模型捕捉到的不是端口号或 IP 之类的「指纹」，而是**通信行为本身的统计规律**，对 IDS 的可迁移性是好消息。

**空闲时间均值（10.79%）位列第二。** 该特征衡量相邻数据包之间最大空闲间隔的均值，反映的是**流的时间节律**。DoS 与 DDoS 以高频、几乎无间隔的方式发包，空闲时间接近 0；PortScan 虽也高频发包，但其「请求—等待响应—再请求」模式会产生规律的小间隔。这解释了模型在随机划分下为何能达到 99.9% 的准确率——攻击与正常流量在时间节律上的差异确实显著。**但它同时也解释了按时间划分的失败**：该特征排名靠前说明模型高度依赖具体的节律数值，当测试期的攻击来自不同工具与带宽条件时节律整体偏移，学到的阈值区间不再适用。**特征本身是有意义的，但模型学到了过窄的阈值**——这可通过数据增强或领域自适应缓解。

**SHAP 分析补充了方向性信息。** 全局重要性只给出「哪个特征重要」，SHAP 还能给出「特征值往哪个方向推动预测」。图 6-1 展示的是一条**被误报的正常流量**（真实 BENIGN → 预测 DoS）的单样本归因。

### 6.5 研究点④：划分方式对评估结果的影响

本节量化「随机划分高估了多少」，这是全文最具警示意义的结论。

**表 6-10 划分方式对评估结果的影响（XGBoost）**

| 任务 | 划分 | 准确率 | 平衡准确率 | 宏 F1 | MCC | 相对随机划分的指标落差 |
|---|---|---:|---:|---:|---:|---|
| 二分类 | 随机 | 0.9992 | 0.9989 | 0.9975 | 0.9971 | — |
| 二分类 | 按时间 | 0.8635 | 0.6823 | 0.5344 | 0.5569 | F1 **−0.4631** |
| 多分类 | 随机 | 0.9992 | 0.9328 | 0.9550 | 0.9972 | — |
| 多分类 | 按时间 | 0.7851 | 0.1666 | 0.1151 | 0.2725 | 宏 F1 **−0.8399** |

**随机划分高估的幅度随任务复杂度急剧放大。** 二分类上宏 F1 高估 0.4631，多分类上高估 0.8399——后者是前者的 1.8 倍。原因在于多分类需要区分 8 个类别，而按时间划分使其中 6 个类别在训练期完全缺席，模型失去了区分它们的能力；二分类只需回答「是否异常」，即使没见过具体攻击类型，仍可依靠「不像正常流量」这一较粗的判断标准完成部分检出。

**准确率是三个指标中最具误导性的。** 二分类按时间划分的准确率仍有 0.8635，而宏 F1 只有 0.5344；多分类按时间划分的准确率 0.7851，宏 F1 只有 0.1151。若只看准确率，会得出「划分方式影响有限」的错误结论。差异来源在于**准确率按样本数加权、被 BENIGN 主导**——多分类测试集中 BENIGN 占 78.53%，故「全判 BENIGN」即得 78.51% 的准确率；按主机划分的测试集中 BENIGN 占 99.82%，故「全判 BENIGN」即得 99.82% 的准确率，而攻击召回率只有 0.1880（见第 5.3 节）。**这两种退化都不是假设，而是在本文实验中被实际观测到的**，因此报告的全部指标始终优先引用**平衡准确率、宏 F1 与 MCC** 三项对不平衡不敏感者。

**结论：** 随机划分下的 99.9% 不能被解读为「模型已可用于生产」。真实部署中攻击手法必然演变、流量分布必然漂移，按时间划分的 0.5344（二分类 F1）才更接近模型的真实下限。这一落差就是本文主张「IDS 评估必须使用时间划分」的量化依据。

### 6.6 四个研究点的横向对照

本章的四个研究点分别从**数据、任务、模型、评估**四个角度考察了同一套模型，其结论之间存在明确的相互印证关系。表 6-11 汇总四者的核心结论与量化依据。

**表 6-11 四个研究点的核心结论对照**

| 研究点 | 核心结论 | 关键量化依据 |
|---|---|---|
| ① 类别不平衡 | 调整损失权重优于合成样本；宏 F1 在此问题上无区分度 | 平衡准确率 0.9328 → **0.9771**（类别加权）；SMOTE 对 Infiltration 零改善；三策略宏 F1 差异 < 0.012 |
| ② 未知攻击泛化 | 模型学到的是攻击指纹，而非正常流量的分布 | 未知攻击检出率 0.0000~0.6854 vs 已知攻击 0.9112~0.9739，平均差距 **0.768**；Bot 零检出 |
| ③ 可解释性 | 模型依赖的是通信行为的统计量，而非身份指纹 | 后向包长标准差 16.46%、空闲时间均值 10.79% 居前两位，前 10 项累计 66.4% |
| ④ 划分方式 | 随机划分严重高估泛化能力，准确率是最具误导性的指标 | 多分类宏 F1 0.9550 → **0.1151**；按主机划分准确率 0.9981 而攻击召回率仅 0.1880 |

**四个研究点在因果上构成一条完整的链条，而不是四个并列的独立实验。** 研究点④揭示了**问题**：随机划分下的指标严重虚高，「99.9% 准确率」是评估方式造成的假象。研究点②**解释了这个问题为什么会存在**：既然模型主要在记忆训练集中出现过的攻击特征，那么一旦测试集出现没见过的攻击类型，性能自然崩塌——按时间划分恰恰使 5 个攻击类在训练期完全缺席。研究点③进一步**指出了记忆的具体内容**：模型记住的是「已知攻击类在包长离散度、空闲节律等维度上的具体数值区间」，因此当测试期的攻击来自不同工具与带宽条件时，这些阈值不再适用。研究点①则从另一维度佐证：少数类检测的瓶颈不是「数据量不够」，而是「稀少但真实的样本携带的信息未被充分利用」——这与研究点②同源，**模型真正缺乏的是对真实数据分布的理解，而不是样本数量**。

**由此得到本文最重要的一条方法论结论：在 IDS 评估中，选择什么指标、用什么方式划分数据，其影响大于选择什么模型。** 表 6-10 中，同一模型在随机与按时间划分下的多分类宏 F1 相差 **0.8399**（0.9550 → 0.1151）；而表 6-2 中三个不同模型在同一划分下的**最大**差距为 **0.1705**（多分类随机划分，XGBoost 0.9550 vs MLP 0.7845）。换言之，**换一种划分方式对结论的影响，是换一个模型的 4.9 倍**。这也是本文坚持引用平衡准确率、宏 F1 与 MCC 而非常规准确率的根本原因。

## 7 系统实现与部署

### 7.1 推理服务

系统后端基于 FastAPI 实现，提供以下接口：

| 接口 | 方法 | 说明 |
|---|---|---|
| `/api/health` | GET | 健康检查 |
| `/api/model` | GET | 当前模型的元信息与训练指标 |
| `/api/detect` | POST | JSON 形式的流量检测 |
| `/api/detect/csv` | POST | 上传 CSV 批量检测 |
| `/api/stats` | GET | 汇总统计 |
| `/api/alerts` | GET | 告警列表 |
| `/api/timeline` | GET | 流量趋势 |
| `/api/top-attackers` | GET | 攻击源排行 |

推理服务层的一个关键设计是**模型与特征管道的强绑定**。开发过程中曾出现过这样的问题：管道路径是从模型文件名推导的（按 `_` 从后往前切分出实验名），但模型名本身含下划线（`random_forest`），推导结果必然错误，最终退化为「使用目录下的第一个管道文件」——而那可能来自另一个实验，标准化基准不同，预测会全部错误且不会有任何报错。

修复方案是把管道路径直接写入模型文件，同时增加基于特征列比对的兜底校验。更重要的是修改了失败策略：**找不到确定的管道时直接报错，而不是猜测**。因为在特征口径错配的问题上，一次明确的失败远比一次静默的错误预测有价值。

### 7.2 告警引擎

告警引擎负责把模型的概率输出转换为运维决策，实现了三个关键机制：

**置信度阈值。** 低于阈值的预测只记录不告警。若模型判定为攻击但置信度仅 0.55，通知运维处理的性价比很低。该阈值是误报率与漏报率的调节旋钮。

**告警去重。** DDoS 攻击每秒可产生上千条流，逐条告警会迅速淹没运维界面，导致「告警疲劳」——最终结果是所有人开始忽略所有告警。系统对同一（源 IP、攻击类型）组合在时间窗内只产生一条告警，其余标记为已抑制。

被抑制的告警仍然入库（标记 `suppressed=1`）而非物理删除：抑制数量本身是有价值的运维指标（若某天突增说明攻击强度变化），且审计时需要完整历史。界面会显式展示被抑制的数量，避免用户误以为告警凭空减少。

**严重级别。** 不同攻击的危害差异显著：PortScan 属于侦察行为，而 Bot 意味着主机已被控制。系统按配置为每类攻击设定严重级别，并在告警消息中附带处置建议。

### 7.3 流量特征提取

系统的实时路径基于 tshark：由 tshark 解析 pcap 或网卡流量并输出字段，Python 端按键值对做双向流聚合，再计算特征。

这里存在一个必须正面处理的工程问题：**无法从 pcap 可靠复现 CICFlowMeter 输出的全部 70 个特征**，因为部分特征依赖工具的私有实现细节——`Fwd/Bwd Avg Bytes/Bulk` 系列依赖其内部的 bulk 判定规则（连续同向包阈值、超时切分），`Subflow Fwd/Bwd *` 依赖 TCP 子流划分逻辑，`Active/Idle` 系列依赖带超时参数的状态机，三者均无公开文档。若强行复现，一旦某个细节算错，模型输入会整体偏移、预测退化为噪声，而且不会有任何报错。

本文采用的方案是**显式定义可验证的特征子集**：实时路径只计算 48 个定义明确、可从包序列直接得出的特征，并在同一数据集、同一子集上训练配套模型，使训练与推理的特征口径天然一致。代价是精度略降，但这条路径上的每个数字都是可信的（量化见第 6 章）。

### 7.4 可视化看板

前端采用纯 HTML 与 ECharts 实现，由 FastAPI 直接托管静态文件。选择这一方案而非 Vue/React 的原因很实际：**没有构建步骤**。课程设计答辩现场的可靠性比技术栈的先进性重要得多——`uvicorn` 启动即可演示，不存在依赖安装失败的风险。ECharts 库文件已本地化（1 MB），断网环境下同样可用。

看板包含以下视图：

- **KPI 指标卡**：检测流量总数、攻击数、告警数、攻击占比；
- **攻击类型分布**：横向条形图，对数刻度；
- **流量趋势**：正常与攻击流量的时间序列折线图；
- **攻击源 Top 10**：帮助运维快速定位攻击主机；
- **告警列表**：含严重级别标记、置信度、处置建议，支持确认操作；
- **最近检测记录**：原始判定结果。

## 8 结论与展望

### 8.1 主要结论

本文完成了基于机器学习的网络入侵检测与实时告警系统的设计与实现，主要结论如下：

**第一，CICIDS2017 存在严重的采样偏差。** 除 Bot（8 个源 IP）与 DDoS（2 个）外，每一类攻击都仅来自**一台攻击机**，后果有二：一是「按源 IP 分组划分」这一常规防泄露评估方法完全失效，会把整个攻击类别推到划分的同一侧；二是任何未说明如何处理该偏差的 CICIDS2017 实验，其泛化能力结论都值得怀疑。

**第二，数据质量问题占据了本项目相当篇幅，且多数不会被报错暴露。** 编码损坏的标签（两个版本损坏形式不同，其中一个在数据生成阶段就已产生）、28.8 万条空标签被读取为字符串 `'nan'`、25.5 万条完全重复的记录、`_source_file` 列造成的隐蔽数据泄露，以及第 8.4 节汇总的 14 个工程问题——它们的共同特征是不会导致程序崩溃，而是让模型给出「看起来很好」的错误结果。

**第三，在类别极度不平衡的数据上，准确率与宏 F1 都可能失效，指标选择本身就会改变结论。** 「全部判 BENIGN」这一毫无检测能力的退化策略，在多分类按时间划分下可得到 **78.51%** 的准确率（恰好等于测试集中 BENIGN 的占比 78.53%），在按主机划分下更是高达 **99.82%**；而第 6.2 节进一步表明，宏 F1 在比较三种不平衡处理策略时差异不足 **0.012**，几乎无法区分策略优劣。**只有平衡准确率（等价于宏召回率）能同时反映「多数类是否被牺牲」与「少数类是否被放弃」**，这是本文全部结论优先引用它的原因。

**第四，模型的未知攻击发现能力有限，高度依赖训练集中是否出现过同类攻击。** 留一类实验中未知攻击检出率为 0.0000~0.6854，已知攻击则为 0.9112~0.9739（平均差距 0.768）；最隐蔽的 Bot 攻击在训练集缺席时实现**零检出**（395 条与 391 条全部被判为正常）。这说明模型的决策边界主要围绕**已知攻击样本**构建，而非围绕**正常流量的分布**。因此在生产环境中本系统必须与签名检测、流量基线告警等手段配合，不能作为独立防线。

### 8.2 系统局限性

**特征层面的局限。** 系统使用的是流统计特征，不具备载荷内容分析能力。对于 SQL 注入、XSS 等依赖具体请求内容的攻击，仅靠流量统计特征难以准确区分，这也是本文实验中 WebAttack 类表现相对较弱的原因之一。

**实时性层面的局限。** 当前实现按「流超时」判定一条流结束，最坏情况下需要等待超时时间才能输出结果。对于需要毫秒级响应的场景，需要引入滑动窗口的部分流特征估计。

**数据层面的局限。** 如第 5.3 节所述，CICIDS2017 的攻击流量在主机维度缺乏多样性，模型在其上学到的模式能否迁移到真实网络环境，是一个未经验证的问题。

### 8.3 未来工作

1. **引入载荷特征。** 对 HTTP 请求的 URI、参数、请求体进行 token 化与统计，弥补当前方案对内容型攻击的检测短板。
2. **时序建模。** 将单条流的分类扩展到流序列，使用 LSTM 或 Transformer 建模主机的行为时序，识别慢速渗透等单流特征不明显的攻击。
3. **在线学习。** 当前模型是离线训练后固定部署的。真实网络中流量分布会随时间漂移，需要考虑增量学习或定期重训练机制。
4. **对抗鲁棒性评估。** 研究攻击者通过调整流量特征规避检测的可能性，这是机器学习型 IDS 面临的现实威胁。

### 8.4 工程实践：问题清单与教训

本节记录项目开发过程中实际遇到并修复的 **14 个问题**。它们不是假设性的注意事项，而是每一个都真实导致过错误结果或程序失败的案例。之所以单独成节，是因为其中**大部分问题的共同特征不是「程序崩溃」，而是「程序照常运行、指标照常输出，只是结果悄悄地错了」**——而后者远比前者危险。

**表 8-1 开发过程中发现并修复的问题清单**

| # | 问题 | 失效方式 | 影响 | 修复与防呆 |
|---:|---|---|---|---|
| 1 | `_source_file` 列漏进特征 | 静默 | 该列与标签高度相关，准确率虚高至 99%+ | 加入 `INTERNAL_COLS` 强制排除 |
| 2 | 数据集版本选错 | 静默 | 精简版无 Source IP，研究点④无法进行 | 改用 `GeneratedLabelledFlows` 版本 |
| 3 | WebAttack 标签编码损坏 | 静默 | 两个版本损坏方式不同，换编码救不回 | 读取时 `errors='replace'` + 按 Unicode 类别剥离 |
| 4 | 28.8 万条空标签被读成 `'nan'` | 静默 | 绕过缺失值判断，清洗流程卡死 | `clean_label` 显式识别 NaN |
| 5 | 同一划分被重复标准化 | 静默 | 第二个模型拿到缩放两次的数据 | `is_transformed` 标记拦截 |
| 6 | XGBoost 二分类崩溃 | 崩溃 | `eval_metric: mlogloss` 让 XGB 按多分类处理 | 目标函数与评估指标按任务成对设置 |
| 7 | 特征管道靠字符串推导路径 | 静默 | 模型名含下划线必然推导错误 | 管道路径写入模型文件 + 特征列校验兜底 |
| 8 | 时间划分下 AUC 崩溃、绘图越界 | 崩溃 | 训练期 3 类却按 8 类索引概率矩阵 | 区分 `classes` 与 `proba_classes` |
| 9 | 二分类留出实验全部被跳过 | 静默 | 目标变量里没有 `Bot`，按目标筛选必然找不到 | 改按原始标签 Series 筛选 |
| 10 | **`class_weight` 对 XGBoost 静默失效** | 静默 | 「加权」与「不处理」两组实验指标**完全一致**，实验白做 | 改走 `fit(sample_weight=...)` + 加防呆检查 |
| 11 | SMOTE 配置与代码不一致 | 报错 | 配置写 `not_majority`，代码拒绝执行该模式 | 配置改 `capped`，`max_rows` 从配置读取 |
| 12 | SMOTE 构造函数传了 `n_jobs=-1` | 被吞掉 | imbalanced-learn 0.14 已移除该参数，抛 `TypeError` | 去掉该参数 |
| 13 | SMOTE 策略键与标签编码不匹配 | 被吞掉 | 键是类别名、实际收到整数编码标签，报「target class not present」 | `build_resampler` 内用同一套 `LabelEncoder` 转换 |
| 14 | **`build_pipeline` 重建 DataFrame 丢弃索引** | 静默 | 回查标签取到**完全无关的行**，研究点②整套结论作废 | 重建时保留索引 + 加入标签对齐断言 |

**问题 10、12、13、14 属于同一类，也是本节最值得记录的一类。**

其中 **#14 最隐蔽**：`build_pipeline` 把特征矩阵原地替换为标准化结果时，用 `pd.DataFrame(...)` 重建了 DataFrame 而未把原索引带回来，索引因此变成 `0..n-1`；调用方随后用 `df.loc[X_test.index, LABEL_COL]` 回查标签，取到的不是测试集，而是**原数据的前 514,740 行**。它的隐蔽之处在于**所有表面证据都正常**——行数正确、类别齐全、训练照常收敛、指标照常输出，唯一破绽是未知攻击检出率**恰好等于测试集中攻击样本的基准占比**（二分类 17.2% vs 基准 16.5%），即模型表现与随机猜无法区分。**#10 的性质完全相同**：`class_weight` 是被 XGBoost 静默丢弃的构造参数，表现为两个策略的全部指标逐位相同，线索同样是「两个本应不同的实验给出了完全一样的数字」。由此得到两条教训。

**第一，「结果看起来合理」不构成任何验证。** #10 与 #14 产出的都是格式正确、量级正确、甚至与文献相符的数字。判断实验是否真的按预期执行，必须依赖**独立于结果的不变量**：例如 #10 最终加的防呆检查会打印实际构造出的样本权重范围（`为 xgboost 构造样本权重（共 8 类，权重范围 0.150 ~ 8908.952）`），只要该日志出现即可确认参数被消费。同理，验证「配置是否被消费」的成本远低于验证「结果是否正确」——一行 `build_model(...).get_params()` 就能确认参数有没有被丢弃，而跑一轮完整实验需要几分钟到几十分钟。

**第二，要主动设计对照组，让异常变得可识别。** 「两个策略指标完全相同」「检出率恰好等于基准占比」这两个信号都极其廉价，但前提是**知道该拿什么作对照**。因此本文设计实验时尽量同时产出一个对照组（如研究点②中的「已知攻击检出率」），它不仅提供对比数字，更是**结果合理性的自检机制**：若未知攻击与已知攻击的检出率几乎相同，「未知」这个前提本身就很可能是假的。

最后，#12 与 #13 还暴露了一个流程问题：两个异常被 `run.py` 中逐策略的 `try/except` 吞掉，只表现为「汇总表里少一行」，容易被误读为「这个策略没必要做」而非「这个策略跑失败了」。为此在收尾处增加了显式统计：

```
⚠ 有 1/3 种策略未能完成：SMOTE 过采样 —— 汇总表与结论中缺少这些策略
```

**一个失败的实验必须以失败的形式出现，而不是以「缺失」的形式出现。** 这是本项目在工程实践上最重要的一条体会。
